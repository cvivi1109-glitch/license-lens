# 协议的适用范围、适配与商用指南

> 本文逐条回答老师提出的四个问题：
> ① 协议之间的**适用范围**是什么？ ② 不同协议之间**怎么适配**？ ③ **判定依据**是什么？ ④ 哪些能**商用**、商用怎么考虑？
>
> 对应 v0.2 的三个新命令：`scope`（适用范围）、`adapt`（适配方案）、`commercial`（商用评估）。

---

## 一、判定依据是什么（证据链）

本工具的所有结论都来自下面三层证据，**不是凭感觉**：

| 层级 | 证据 | 权威性 | 本工具怎么用 |
|------|------|--------|--------------|
| 第 1 层 | **许可证原文条款** | 最高（授权的法律文本本身） | `basis` 字段逐条登记条款号，如 GPL-3.0 §5/§6/§11 |
| 第 2 层 | **OSI 认证 / FSF 兼容性列表 / SPDX 标识** | 高（行业公认标准） | 记录 `osi_approved`、`fsf_free`、SPDX 名称 |
| 第 3 层 | **choosealicense.com 等官方 FAQ** | 参考（解释性材料） | 用于商用说明与选型建议 |
| 第 4 层 | 本国法律与司法实践 | 最终（但超出工具范围） | 工具明确声明"不构成法律意见" |

### 1.1 判定规则怎么来的

| 判定结论 | 依据 | 例子 |
|----------|------|------|
| 宽松 → 任何许可，**允许** | 宽松许可允许再许可/并入更强许可，义务随作品继续存在 | MIT → GPL-3.0 |
| 传染 → 宽松，**禁止** | 传染许可要求衍生作品同样开源，无法"降级" | GPL-3.0 → MIT |
| 弱传染看链接方式 | LGPL §4 对组合作品的定义 | LGPL 动态链接可闭源；静态链接不行 |
| 网络服务触发 | AGPL §13 的远程交互条款 | AGPL 的 SaaS 必须提供源码 |
| 非商业许可 | CC BY-NC §2(a)(1) 仅授予非商业使用 | CC-BY-NC → 商用 ❌ |
| 无法确定 | 工具不猜，输出"有条件 + 人工确认" | 未登记的组合 |

### 1.2 为什么"判定依据"必须写进工具

本质是：**你的结论能不能被验证**。
所以 v0.2 让每条判定都带法源：

```powershell
python -m license_lens check GPL-3.0 MIT
```

```
❌ [禁止] 上游 GPL-3.0  →  我的项目 MIT（dynamic）
   依据：GPL-3.0 具有强传染性，衍生作品必须同样开源；以 MIT 发布违反了这一义务。
   法源（来自上游 GPL-3.0）：
     - GPL-3.0 §5：向下游传递授权，衍生作品必须同样以 GPL 发布
     - §6：分发目标代码时须提供对应源码
     - §7：不授予商标权
     - §11：专利授权
     - FSF 兼容性列表：GPL-3.0 与 MIT / BSD-3 / Apache-2.0 兼容，与 GPL-2.0-only 不兼容
```

### 1.3 一个必须说清的边界

许可证是**授权的合同文本**，不是法律本身。同一个问题在不同法域可能有不同解释，尤其是：

- "什么构成衍生作品"（GPL 的经典争议）
- "进程隔离算不算链接"（无统一判例）
- "内部使用算不算分发"

所以本工具对这类问题一律标注"**边界存在争议，需咨询法律意见**"，而不是给一个漂亮但危险的"通过"。

## 二、协议之间的适用范围（它到底管什么）

### 2.1 用五个维度看一份许可证

| 维度 | 要问的问题 | 典型差异 |
|------|------------|----------|
| **著作权** | 覆盖源代码？文档？修改版？ | 几乎都覆盖代码 |
| **专利** | 有没有明示专利授权？ | Apache/MPL/GPL 有；MIT/BSD 无 |
| **商标** | 能不能用作者/项目名称背书？ | **全部都不授予**；Apache/MPL 明确排除 |
| **分发方式** | 源码分发 vs 二进制分发义务是否不同？ | GPL/AGPL 要求提供源码；MIT 只需留声明 |
| **使用方式** | 内部分发？链接？网络服务？ | LGPL 看链接；AGPL 看网络服务 |

### 2.2 九种许可证横向对比

| 许可证 | 覆盖范围 | 专利授权 | 商标授权 | 源码义务 | 链接传染 | 网络服务 | 商用 |
|--------|----------|----------|----------|----------|----------|----------|------|
| **MIT** | 代码/文档/再分发 | ❌ 无 | ❌ 无 | 无 | 无 | 否 | ✅ 允许 |
| **BSD-3-Clause** | 代码/再分发 | ❌ 无 | ❌ 无（禁背书） | 无 | 无 | 否 | ✅ 允许 |
| **Apache-2.0** | 代码/文档/专利 | ✅ 有（§2） | ❌ 明确排除（§6） | 无 | 无 | 否 | ✅ 允许 |
| **LGPL-3.0** | 库本身 + 链接方式 | ✅ 有 | ❌ 无 | 修改库/静态链接时 | **弱** | 否 | ⚠️ 有条件 |
| **MPL-2.0** | 文件级 | ✅ 有 | ❌ 无 | 修改过的文件 | 弱（文件级） | 否 | ✅ 允许 |
| **GPL-3.0** | 衍生作品 + 分发 | ✅ 有（§11） | ❌ 无（§7） | **对外分发时** | **强** | 否 | ✅ 允许（有源码义务） |
| **AGPL-3.0** | 衍生作品 + **网络服务** | ✅ 有（§11） | ❌ 无 | **分发或提供服务时** | **强** | **是（§13）** | ✅ 允许（SaaS 须开源） |
| **BUSL-1.1** | 源码可见 + 生产受限 | 视版本 | ❌ 无 | 无（限制使用而非开源） | — | — | ⚠️ 受限 |
| **CC-BY-NC-4.0** | 文档/作品 | ❌ 无 | ❌ 无 | 无 | — | — | ❌ 禁止 |

### 2.3 每种许可的"边界"详解

**MIT** —— 管得最少
- 管：复制、修改、分发时的**署名**。
- 不管：专利、商标、担保。
- 边界：引用了 MIT 代码，你的项目仍然可以是闭源的；只要保留那段版权声明。

**Apache-2.0** —— 多一层专利保护
- 管：署名 + NOTICE + 修改标注 + **专利授权**。
- 不管：商标（§6 明确排除）、担保。
- 边界：如果贡献者对你发起专利诉讼，你对他的专利授权会终止（§3）。

**BSD-3-Clause** —— MIT + 禁背书
- 管：署名 + 二进制再分发保留声明 + **不得用作者名背书**。
- 不管：专利、商标。
- 边界：与 MIT 最大区别是第 3 条"禁止背书"。

**GPL-3.0** —— 管"衍生作品"
- 管：修改、链接、合并形成的**整体作品**必须同样 GPL；对外分发必须提供源码。
- 不管：内部使用（不分发不触发）、网络服务（那是 AGPL 的事）、商标。
- 边界：**关键在于"衍生作品"的认定**。静态/动态链接通常都算；独立进程/服务调用存在争议。

**LGPL-3.0** —— 管"库"，且看链接方式
- 管：修改库本身必须以 LGPL 开源；静态链接需提供重链接方式。
- 不管：动态链接下的独立程序。
- 边界：**动态链接可以闭源，静态链接不行**，这是最容易被忽略的一条。

**AGPL-3.0** —— GPL + 网络服务
- 管：GPL 的全部义务 + **通过网络提供服务时也要提供源码**。
- 边界：SaaS 场景下，AGPL 比 GPL 严格得多。

**MPL-2.0** —— 文件级传染
- 管：被 MPL 覆盖的文件被修改后，该文件需以 MPL 公开。
- 不管：项目里其他文件可以用别的许可。
- 边界：适合"想开源自己但允许别人闭源集成"的混合场景。

**BUSL-1.1** —— 源码可用，但不是开源
- 管：生产环境使用受限，Change Date 后转为指定开源许可。
- 边界：**不是 OSI 认可的开源许可证**，商用前必须看清限制条款与转换日期。

**CC-BY-NC-4.0** —— 非商业
- 管：仅非商业用途 + 署名。
- 边界：**不是软件许可证**，也不符合开源定义；一旦涉及营利业务即违约。

### 2.4 三个最容易误判的边界

| 场景 | 很多人以为 | 实际 |
|------|------------|------|
| 公司内部使用 GPL 软件 | 必须开源 | ❌ 内部使用不分发，通常不触发源码义务 |
| 用 GPL 做 SaaS | 必须开源 | ❌ GPL-3.0 不要求；**AGPL 才要求** |
| 静态链接 LGPL 库 | 可以闭源 | ❌ 静态链接需提供重链接方式，或以 LGPL/GPL 开源 |

## 三、不同协议之间怎么适配（6 种手段）

### 3.1 一条总原则

```
宽松  ──可以并入──▶  传染         ✅
传染  ──不能并入──▶  宽松         ❌
```

也就是：**MIT/BSD/Apache 的代码可以放进 GPL 项目；GPL 的代码不能放进 MIT 项目。**

所以适配的方向永远是两种：
1. **提高自己项目的许可强度**（改项目许可）
2. **降低依赖的许可强度**（换依赖 / 改链接方式 / 买商业授权）

### 3.2 六种适配手段

| # | 手段 | 适用场景 | 效果 | 风险 / 代价 |
|---|------|----------|------|-------------|
| 1 | **改项目许可** | 依赖是 GPL/AGPL | 立即可用，最稳妥 | 你的项目也必须开源 |
| 2 | **改动态链接** | 依赖是 LGPL | 可闭源 | 必须允许使用者替换该库 |
| 3 | **进程 / 服务隔离** | 依赖是 GPL/AGPL | 可能避开"衍生作品" | **法律边界有争议**，需律师确认 |
| 4 | **替换依赖** | 任意冲突 | 彻底解决 | 开发/迁移成本 |
| 5 | **双许可选择** | 依赖提供双许可 | 选对你有利的那一个 | 需确认你满足该许可条件 |
| 6 | **购买商业授权** | 依赖提供商业许可 | 获得豁免 | 有预算成本 |
| 7 | **仅内部使用** | 不分发 | 通常不触发 GPL 源码义务 | 一旦对外分发/服务需重新评估 |

### 3.3 五个真实组合案例

#### 案例 1：GPL-3.0 的库 + 想用 MIT 发布
```powershell
python -m license_lens adapt GPL-3.0 MIT
```
**判定**：❌ 禁止
**改法**：
1. 把项目改为 GPL-3.0（推荐，最简单）
2. 换掉这个依赖
3. 拆成独立进程/服务（有争议）
4. 仅内部使用、不对外分发
5. 购买商业授权

#### 案例 2：LGPL-3.0 的库 + 闭源商业产品
```powershell
python -m license_lens adapt LGPL-3.0 MIT --linkage static
```
**判定**：❌ 禁止（静态链接）
**改法**：改成**动态链接**即可（推荐）——这是 LGPL 设计的初衷：
> 让你能闭源使用，但必须允许别人替换这个库。

#### 案例 3：Apache-2.0 的库 + GPL-3.0 项目
```powershell
python -m license_lens check Apache-2.0 GPL-3.0
```
**判定**：✅ 允许
**注意**：Apache-2.0 与 **GPL-2.0-only** 不兼容（专利条款冲突），但与 GPL-3.0 兼容。这是最容易被搞混的一条。

#### 案例 4：MIT 的库 + 闭源商业软件
```powershell
python -m license_lens check MIT MIT
```
**判定**：✅ 允许
**义务**：保留版权与许可声明即可。**MIT 不限制商用，也不要求开源你的代码。**

#### 案例 5：AGPL-3.0 的库 + SaaS
```powershell
python -m license_lens commercial AGPL-3.0
```
**判定**：⚠️ 有条件 —— 只要通过网络提供服务，就必须向用户提供完整源码。
**改法**：换依赖 / 买商业授权 / 接受开源。

### 3.4 适配之后别忘了义务清单

适配方案解决的是"**能不能用**"，义务清单解决的是"**用了之后要做什么**"：

```powershell
python -m license_lens obligations Apache-2.0
```

```
- [ ] 保留版权与许可声明
- [ ] 随分发提供 NOTICE 文件（若上游提供）
- [ ] 标明被修改过的文件
- [ ] 专利授权：使用者自动获得贡献者的专利许可
- [ ] 不得使用 Apache 商标进行背书宣传
```

## 四、商用怎么考虑

### 4.1 先纠正一个最大误区

> **开源 ≠ 不能商用。**

OSI 认可的 5 种课堂许可（MIT / BSD-3 / Apache-2.0 / GPL-3.0 / LGPL-3.0）**全部允许商用**，包括收费销售。
真正的问题不是"能不能卖"，而是"**卖了之后要付出什么代价**"。

| 许可证 | 能商用吗 | 代价 |
|--------|----------|------|
| MIT / BSD-3 | ✅ 能 | 保留声明（几乎无成本） |
| Apache-2.0 | ✅ 能 | 保留 NOTICE + 修改标注 |
| LGPL-3.0 | ✅ 能 | 动态链接 + 允许替换库 |
| GPL-3.0 | ✅ 能 | 对外分发时公开源码，衍生作品同样 GPL |
| AGPL-3.0 | ✅ 能 | 提供网络服务时公开源码 |
| BUSL-1.1 | ⚠️ 受限 | 生产使用通常需商业授权 |
| CC-BY-NC / PolyForm-NC | ❌ 不能 | 仅限非商业用途 |

### 4.2 按商业模式选许可证

| 你的商业模式 | 推荐许可 | 原因 |
|--------------|----------|------|
| 卖闭源软件 | MIT / Apache-2.0 / BSD-3 | 无源码义务，客户可闭源集成 |
| 卖 SaaS 且不想开源 | MIT / Apache-2.0 / BSD-3 | 避免 AGPL 的网络服务条款 |
| 卖 SaaS 且愿意开源 | AGPL-3.0 | 防住"拿去做云服务不开源" |
| 卖技术支持 / 定制开发 | GPL-3.0 也可以 | 软件开源，服务收费是常见模式 |
| 开源核心 + 商业版（open core） | 核心用 MIT/Apache | 核心可自由使用，商业版闭源增值 |
| 硬件 / 嵌入式产品 | MIT / Apache-2.0 | 避免 GPL 的整机开源风险 |
| 公司内部系统 | 任意（含 GPL） | 内部使用不分发，义务最轻 |
| 课程 / 作业项目 | **MIT**（推荐） | 老师明确说"工具/作业首选之一"，义务最少 |

### 4.3 商用前的 8 项检查清单

- [ ] 列出**全部**依赖及其许可证（`python -m license_lens scan deps.txt`）
- [ ] 确认是否**对外分发二进制**（分发才触发 GPL 义务）
- [ ] 确认是否**提供网络服务**（触发 AGPL §13）
- [ ] 确认是否**静态链接** LGPL 库（是则需处理）
- [ ] 确认是否**修改**过 LGPL/MPL 的库文件
- [ ] 确认代码里是否含**专利技术**（MIT/BSD 没有专利授权）
- [ ] 确认是否使用了他人的**商标/项目名**做宣传
- [ ] 确认是否有 CLA / 贡献者授权（公司项目尤其重要）

### 4.4 五个常见误区

| 误区 | 事实 |
|------|------|
| "开源就是不能商用" | ❌ 所有 OSI 许可都允许商用 |
| "GPL 不能卖钱" | ❌ GPL 允许收费，只是要提供源码 |
| "MIT 项目里可以随便放 GPL 代码" | ❌ 强传染，会把整个项目拖成 GPL |
| "AGPL 和 GPL 差不多" | ❌ AGPL 多了一条网络服务条款，SaaS 场景差别巨大 |
| "内部使用也要开源" | ❌ 不分发通常不触发 GPL 源码义务 |
| "改个变量名/换种语言就不算衍生作品" | ❌ 衍生作品的认定看实质，不看表面改写 |

### 4.5 本工具对应的命令

| 关注点 | 命令 | 输出 |
|--------------|------|------|
| 每种协议管什么 | `python -m license_lens scope GPL-3.0` | 覆盖范围 / 不覆盖 / 专利商标 / 源码义务 / 法源 |
| 两两能不能混 | `python -m license_lens check GPL-3.0 MIT` | 判定 + 法源 + 改法提示 |
| 不能混怎么办 | `python -m license_lens adapt GPL-3.0 MIT` | 5~6 条具体改法 |
| 能不能商用 | `python -m license_lens commercial GPL-3.0` | 按场景列出"可以/不可以/有条件" |
| 全部许可的商用结论 | `python -m license_lens commercial` | 一张总表 |
| 整份依赖清单 | `python -m license_lens scan deps.txt` | 合规报告 + 义务清单 |

## 五、结论

1. **适用范围的本质**：许可证管的是"著作权 + 专利 + 商标 + 分发 + 使用方式"五个维度，不同许可证在这五个维度上的覆盖不同。
2. **适配的本质**：宽松可以并入传染，传染不能降级为宽松；所以要么提高自己的许可强度，要么降低依赖的许可强度。
3. **判定的依据**：许可证原文条款（第一层）+ OSI/FSF/SPDX（第二层）+ 官方 FAQ（第三层），每一条结论都可追溯。
4. **商用的本质**：开源许可全部允许商用，区别在于"商用后要付出什么"——MIT 几乎零成本，GPL/AGPL 要用开源的代价换，BUSL/CC-NC 则直接限制。

> 免责声明：本文与工具均为技术辅助，不构成法律意见。涉及重大商业决策时，请咨询专业律师。
